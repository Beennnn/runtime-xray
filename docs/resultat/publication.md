# Publishing the report — which channels, and which really work

> Starting question: *"can this be done in git? a GitHub file, or a space under GitHub?"* —
> Answer: **yes, in four different ways**, three of them tested here. They are not
> equivalent.

## ⚠️ First, the limit that overrides everything

**GitHub is online.** In a genuinely disconnected environment, no GitHub channel works. They
are useful for this study repository, for a team that has access to a forge, or for an
internal forge (a self-hosted GitLab offers the same mechanisms).

In a cut-off environment, only the **carried file** remains — and that is precisely what
channel no. 3 produces. It is also what was retained as the main channel.

## The problem: GitHub displays HTML as source code

Clicking a `.html` in the GitHub interface shows its tags, not the page. This is deliberate
(displaying arbitrary HTML from a repository would be a hole), and no setting works around
it. Four answers, from the best to the most rickety:

| Answer | What it gives | Status |
|---|---|---|
| **A Markdown summary** — [`runtime-xray-out/rapport.md`](../../reports-demo/executions/rapport.md) | GitHub renders it **natively**, including on a private repository, with no Pages and no third-party service. Coverage tables, most costly methods, captured values | ✅ in place |
| **GitHub Pages** | The real report, rendered, at a URL | ✅ in place |
| **A release's zip** | The complete report, offline | ✅ in place |
| `htmlpreview.github.io` | A proxy that renders a repository's raw HTML | ⚠️ third-party service, online, often breaks on linked resources — **not retained** |

**Markdown is the only answer that works inside GitHub**, without depending on Pages or on a
third party. It is generated by the orchestrator, in the same pass as the HTML page and from
the tools' *machine* outputs — JaCoCo's CSV, async-profiler's folded stacks, Arthas's
capture. Nothing in it is typed in by hand.

Its limit is real: it is a **summary**. One sees the figures and the ranking there, not the
code coloured line by line. For that, Pages or the zip is needed.

> Note: **SVG, for its part, displays natively in GitHub** — hence this repository's
> diagrams. A flame graph exported as SVG rather than HTML would therefore be seen directly
> in the forge. async-profiler produces HTML; converting from the `collapsed` format to an
> SVG is possible with the historic FlameGraph tooling. A track not explored here.

## 1. The files versioned in the repository — ✅ tested

The reports are committed in [`reports-demo/generated/`](../../reports-demo).

**What it gives**: history. Today's coverage can be compared to that of three months ago, and
a `git diff` on the CSV shows exactly which classes changed status.

**The limit, and it is decisive for reading**: GitHub displays a `.html` file as **source
code**, not as a rendered page. Clicking `index.html` in the GitHub interface gives raw,
unreadable HTML. Versioning serves to archive and to compare, **not to consult**.

## 2. GitHub Pages — ✅ tested, in service

**→ [beennnn.github.io/runtime-xray](https://beennnn.github.io/runtime-xray/)**

A `gh-pages` branch containing the reports, served as a real site. The HTML is rendered, the
navigation works, one shares a URL.

**What it gives**: the most immediate channel — a link, nothing to download, nothing to
install, including from a phone.

**The limits**: the site is **public** if the repository is (private Pages belongs to the
paid offers); and the branch has to be republished at every new run.

## 3. A release with the report attached — ✅ tested, **the channel retained**

**→ [Release rapport-2026-08-20](https://github.com/Beennnn/runtime-xray/releases/tag/rapport-2026-08-20)**
— `rapport-runtime-xray.zip`, **266 KB**.

This is exactly decision no. 3: *a folder sent as one file, analysable without IntelliJ*. The
zip contains the four panels, numbered, with a `LISEZ-MOI.txt` that says what to open first:

```
rapport-runtime-xray/
├── LISEZ-MOI.txt
├── 1-couverture-code-execute/    ← open index.html
├── 2-couverture-complete/
├── 3-arbre-appel/
└── 4-valeurs-parametres/
```

**What it gives**: a self-contained object, dated, carriable — by USB stick, by mail, by
network share. It survives the Internet being cut, which neither Pages nor the forge does.

**The command**:

```bash
gh release create rapport-$(date +%F) rapport-runtime-xray.zip \
  --title "Dynamic analysis report — $(date +%F)"
```

**The limit**: nothing is rendered online, one has to download and unzip. That is the price
of self-containment.

## 4. A GitHub Actions workflow artefact — 📄 not tested here

A workflow that replays the collectors at each run and publishes the zip as an artefact.

**What it gives**: the report becomes automatic, attached to a precise commit.

**The limits**: limited retention (90 days by default), downloading reserved to people signed
in to GitHub, and **on a private repository the minutes are billed**.

## 5. The report served by the tool itself — ✅ tested

The orchestrator can serve its own output directory:

```bash
# on one's own machine
java -jar runtime-xray.jar --report-only --out runtime-xray-out --serve

# on an internal machine where the results are dropped
java -jar runtime-xray.jar --report-only --out /srv/runtime-xray --serve 8080 --serve-host 0.0.0.0

# the same, closed by a drawn shared secret displayed once
java -jar runtime-xray.jar --report-only --out /srv/runtime-xray --serve 8080 \
  --serve-host 0.0.0.0 --serve-token
```

**What it gives**: the only channel that is at once **rendered, offline and shared**. No
forge, no third-party service, nothing to unzip — an internal URL. And it is the only one
where the page can **write**: the names, descriptions, labels and prunings entered by some
are seen by the others, each annotating their runs in parallel. See [Annotating the
runs](../outil/annotations.md).

**The limits**: open, it authenticates nobody — it says so at startup as soon as it listens
beyond the local loopback. `--serve-token` lays down a shared secret, with an entry page and
a twelve-hour session; but a shared secret **says who may come in, not who wrote what**, and
over plain HTTP it travels in the clear. It complements the company's access filtering, it
does not replace it — see [what that secret is
worth](../outil/annotations.md#what-that-secret-is-worth-and-what-it-is-not). And it is a
process to keep alive, where a zip asks nothing of anyone.

## What GitHub cannot do

**Display the coverage in a pull request's diff** — not natively. A third-party service is
needed (Codecov, Coveralls), hence an outbound connection, hence incompatible with the
offline constraint.

**GitLab, for its part, does it natively** from a report in the Cobertura format, and
self-hosts. If the internal forge is a GitLab, this channel becomes available again — it is
the only known way of seeing the covered lines directly in a code review, offline.

**No forge can display a call tree or parameter values.** For those, the self-contained file
remains the only channel.

## Recap

| Channel | Readably rendered | Offline | Self-contained | Tested |
|---|---|---|---|---|
| Versioned files | ❌ raw source | ❌ | ❌ | ✅ |
| GitHub Pages | ✅ | ❌ | ❌ | ✅ |
| **Release + zip** | ✅ after unzipping | ✅ | ✅ | ✅ |
| **Served by the tool** (`--serve`) | ✅ | ✅ | ❌ process to keep alive | ✅ |
| Actions artefact | ✅ after unzipping | ❌ | ✅ | 📄 |
| PR diff | ❌ on GitHub · ✅ on GitLab | ✅ if internal GitLab | ❌ | 📄 |

The zip remains the channel retained for **handing on** a report: it asks nothing of anyone.
`--serve` is the one that suits when several people have to **work on** the same runs,
because it is the only one where what they say about them is kept.
